# 评审协议

## 角色与范围

- 从 `SKILL.md` 的角色表选择与本次改动直接相关的 2–4 个角色视角，不固定全员参加；视角数量不等于 Agent 数量，普通评审由单子 Agent 承担 1–2 个角色。
- 表达式求值、模板 JSON 输入、渲染服务/MCP 对外暴露面、敏感打印数据命中时纳入 `security-expert`；模板契约版本、schema 迁移、存量模板兼容、npm 发布链路命中时纳入 `release-compat-engineer`。
- 条件角色优先替换低相关角色；确实需要超过 4 位时，先向用户说明成本和理由。
- 高风险或用户明确要求时增加 `code-reviewer`；普通局部评审不强制质量门。

## R1：分角色评审

每个角色最多 3 条发现，只返回以下内容；不得复制 spec/plan 原文或完整分析过程：

```text
结论：一句话判断及是否阻塞
证据：文件:行 / 命令输出 / 既有校验结果
风险与未知：按影响排序，区分事实、推导、假设
建议：最小可执行修正；无修正则写“无”
独立性：independent / reused-context / single-agent
置信度：high / medium / low + 原因
```

- 至少一条本人核实的证据；没有证据时降低置信度，不把假设写成结论。
- 角色只指出本次范围内问题；存量问题单独标注，不借评审扩大改动。
- 主持人原样保留分歧，先核证据再裁决，不以多数票代替技术判断。

## R2：按需复核

仅在以下情况启动：

- 两个角色对高影响结论存在证据冲突。
- R1 提出阻塞项，需要补证据或复验修正。
- 高风险议题仍有未覆盖的安全、契约兼容或回滚问题。

无上述情况时记录“无分歧、无阻塞，R2 不启用”。不得要求角色必须找到反例或 Warning。R2 默认复用原子 Agent，只发送阻塞项与新增证据；需要独立反证时才使用新上下文。

## 质量门（按需）

`code-reviewer` 对 spec 与 plan 给出：

- `Pass`：证据完整，无未闭环问题。
- `Warning`：存在非阻塞风险，已写入 plan 风险与应对。
- `Critical`：存在实施前必须解决的问题，逐条附坐标和闭环方式。

任何议题都允许 `Pass`，但没有验证证据不能给 `Pass`。Critical 修正后由原角色或同角色新上下文复核一次；仍未闭环则停止实施并交用户裁决。

## 评审记录

追加到被评审的 spec 或 plan 文末，不另建强制文件：

```markdown
## 专家二次评审（YYYY-MM-DD HH:MM）

- 评审对象与版本：
- 运行方式：主 Agent / 单子 Agent / 按需独立子 Agent；串行或实际并行
- 参与角色及未覆盖范围：
- 用户前置批准：

### 角色结论
<逐角色摘录结论、证据、独立性与置信度>

### 分歧与阻塞项
| 编号 | 结论/证据 | 提出角色 | 状态 | 复核证据 |
|---|---|---|---|---|

### 主持人裁决
<采用、驳回、保留的取舍及依据>

### 用户批准
<批准原文或明确待批准>
```

计划评审另记质量门结论；没有启用时写“不适用：非高风险且用户未要求”。
