# 三端渲染一致性方案

本文面向使用方、集成方与维护者，说明 worm-vue3-print 如何保证**浏览器预览、
服务端 PDF、桌面客户端出纸**三条链路渲染一致：承诺边界、历史问题、架构方案、
保障机制、接入约束与排查方法。

## 一、承诺与边界

**承诺：逻辑同源。** 三端所有「目的相同」的打印逻辑在 `@worm-vue3-print/core`
中只有一份实现，包括：

- 数据绑定与表达式求值、系统变量、表格明细展开与小计/汇总；
- HTML/CSS/SVG 生成、矢量水印瓦片、码制（条形码/二维码）渲染算法；
- 元素实测高度读取与 px→mm 归一化、分页算法；
- 连续纸内容高度探针与纸高推导（含最小高度）；
- 纸张解析与覆盖逃生门、单位换算（px/mm/英寸/μm）；
- PDF 目标规格推导（纸张、边距、背景色精确打印、缩放）；
- 管线编排时序、就绪等待、超时与统一失败分类。

各端只保留**宿主 I/O 适配**：浏览器操作 iframe，服务端驱动 Playwright 页面，
客户端驱动 Electron 隐藏窗口与系统打印命令；适配层内不允许出现任何业务规则。

**不承诺：不做同源控制的像素一致。** 浏览器内核版本不同、工位/容器未安装模板所用字体时，
文字度量差异会级联为换行与分页差异；字体宽度还会影响条形码 SVG 的固有宽度
（jsbarcode 宽度取 `ceil(max(文字宽, 条码宽))`）。因此对外口径是：

> 逻辑同源保证布局算法一致；**像素级一致还要求字体与 Chromium 内核同源**。

跨端产物的自动比对也据此设计为比对**页数与每页 MediaBox（纸张尺寸）**，
文字/条码的位图差异属于已知字体残留差异（见第四节）。

## 二、历史回顾：统一前三端为何会不一致

管线统一（2026-09）之前，三端各自持有一部分打印逻辑，属于「同一目的被实现多次」的结构性问题：

| 环节 | 当时现状 | 后果 |
|---|---|---|
| 管线编排（绑定→测量→分页→HTML） | 浏览器 `browser-pagination` 与服务端 `pdf-render` 两份 | 行为随两份代码各自演化 |
| 预测量读取（元素高度、表格行高、重复表头高） | 两份等价代码 | 测量口径容易漂移 |
| 就绪等待（字体/图片） | 策略不同：浏览器 3s 兜底，服务端 networkidle + 30s | 慢字体/慢图时分页结果不同 |
| 连续纸探针与纸高推导 | 只有浏览器端有 | 同一连续纸模板：客户端按内容高度出纸，服务端固定输出 80×297mm 并**截断内容** |
| 码制渲染 | 浏览器 jsbarcode/qrcode、服务端 bwip-js 两套实现 | 同一码值两端生成几何不同的 SVG |
| HTML→PDF 参数推导 | 客户端按 μm→英寸、服务端按 mm，两份 | 边距/缩放/背景参数分叉 |
| 纸张解析与覆盖逃生门 | 只有客户端有 | 服务端无法处理异常纸型 |
| 截图渲染 | 只有服务端有 | —— |

统一的目标是：以上全部收敛进 core；Express/浏览器池、Electron 窗口池/托盘/串行锁、
WebSocket 协议与 SDK、系统出纸命令与 CUPS 媒体名映射等宿主能力留在各端。

## 三、架构方案

### 1. 分层与端口抽象

```
┌─────────────────────────────────────────────────────────┐
│                    调用方 / 宿主 UI                        │
│  PrintHtmlPreview(canvas)  render 服务 HTTP  客户端 WS     │
├──────────────┬──────────────────────┬───────────────────┤
│ iframe driver│ Playwright driver    │ Electron driver   │  ← 仅宿主 I/O
│ (core/browser)│ (services/print-render)│ (clients/.../main)│
├──────────────┴──────────────────────┴───────────────────┤
│        core 打印管线（print/）：唯一业务规则实现            │
│  pipeline · dom-host-runtime · measure · codes · paper    │
│  pdf-spec · units · errors                                │
├─────────────────────────────────────────────────────────┤
│        core 渲染层（render/）：绑定/HTML/CSS/水印/分页      │
│        core 表达式引擎：lexer/parser/evaluator            │
└─────────────────────────────────────────────────────────┘
```

**driver 契约**（`print/driver.ts`）：`PageDriver` 定义页面打开、载入 HTML、
注入执行器、求值、PDF、截图、关闭等能力；`requiresExecutor` 标识是否需要注入
core 执行器产物（浏览器 iframe driver 进程内直调，置 false）。

**会话模型**（`print/ports.ts`）：`PrintRuntime.withSession(budget, fn)` 负责借用/释放文档槽位
（服务端借还浏览器池页面、客户端复用常驻隐藏窗口、浏览器建/销 iframe），
会话内提供五个业务无关的原语：

- `renderCodes(specs)`：码值 → SVG 映射，支持「收集→渲染→再生成」两趟，缺键降级文本占位；
- `measure(html, viewport)`：载入 → 注入执行器 → 等待就绪 → 读取测量值；
- `probeContentBottom(html, viewport)`：连续纸内容底部探针；
- `toPdf(html, spec, viewport)` / `toScreenshot(...)`：driver 未实现出图能力时抛 `UNSUPPORTED_RUNTIME`。

**共享 DOM 宿主 runtime**（`print/dom-host-runtime.ts`）：
`createDomHostRuntime(driverFactory)` 是三端共用的编排实现，全局时序、超时、错误归一化只在此出现。

### 2. 共享 DOM 执行器

测量、就绪等待、探针、码制渲染的页面内逻辑只有一份实现：`browser/dom-executor.ts`，
编译为 IIFE 产物（`dom-executor.iife.ts`，挂载 `globalThis.__wormDom`）注入隔离页面。

关键语义：`setContent` 会重建文档，此前注入的执行器随之失效，因此**每次 `setContent`
之后都必须重新注入**；「幂等」指同一文档内不重复注入，而非同一会话只注入一次。

### 3. 统一规格与错误

- `print/paper.ts`：纸张解析、宿主覆盖逃生门（`escapeHeightMm`）、µm↔mm、视口 px 推导；
- `print/pdf-spec.ts`：`buildPdfTargetSpec` 统一推导，再由
  `toElectronPrintToPdfOptions`（英寸）与 `toPlaywrightPdfOptions`（mm）分别映射——
  **规格一份，参数映射两处纯换算**；
- `print/units.ts`：全部单位换算的唯一来源；
- `print/errors.ts`：统一失败码 `INVALID_PAPER`/`MEASURE_FAILED`/`RENDER_TIMEOUT`/
  `PDF_FAILED`/`SCREENSHOT_FAILED`/`UNSUPPORTED_RUNTIME`/`INTERNAL`，各端只做协议映射不新增码；
- 默认预算：超时 30s（`DEFAULT_TIMEOUT_MS`）、就绪等待 5s（`DEFAULT_READINESS_MS`）。

### 4. 三端接线对照

| | 浏览器预览 | render 微服务 | Electron 客户端 |
|---|---|---|---|
| driver | `browser/driver-iframe.ts` | `services/print-render/src/driver-playwright.ts` | `clients/print-client/src/main/driver-electron.ts` |
| runtime 装配 | `createBrowserPrintRuntime()` | `pdf-render.ts` 装配 | `print-engine.ts` 装配 |
| 页面槽位 | 隐藏 iframe，用完销毁 | `BrowserPool` 借还 | 常驻隐藏窗口槽位 |
| 出图 | 不支持 PDF，组件内 `window.print()` | `page.pdf()` / `page.screenshot()` | `printToPDF` 后交 `pdf-printer.ts` 系统命令出纸 |
| 调用入口 | `renderHtmlPages`（薄包装，签名不变） | HTTP `/render/pdf`、`/render/screenshot` | WS `print.submit` / `print.submitHtml` |

`renderHtmlPages` 保留第 4 参数 `CodeRenderer` 的覆盖语义：调用方传了渲染器就沿用
（canvas 预览与 demo 均显式传入 `browserCodeRenderer`），不传才由 runtime 自建。

## 四、一致性保障机制

### 1. 架构守卫（强制，静态）

`scripts/check-print-architecture.mjs`（根命令 `npm run lint:print-architecture`）扫描
`services/print-render/src` 与 `clients/print-client/src`，白名单仅允许 driver/平台适配层
（`driver-electron.ts`、`driver-playwright.ts`、`pdf-printer.ts`、测试文件），禁止：

| 禁止模式 | 原因 |
|---|---|
| `offsetHeight` / `getBoundingClientRect` | DOM 测量必须走 core 执行器 |
| `composeContinuousHeight` / `MIN_CONTINUOUS_HEIGHT_MM` | 连续纸推导必须在 core |
| `import 'jsbarcode'/'qrcode'/'bwip-js'` | 码制渲染必须走 core 执行器 |
| `printBackground:` / `preferCSSPageSize:` | 出图参数必须来自 core 的 PDF 规格 |
| `printToPDF(` / `page.pdf(` | 出图调用只能出现在 driver 内 |

新增「三端各写一遍」的代码会直接让守卫失败。

### 2. 跨端产物比对（发布前人工执行）

`services/print-render/src/cross-end.parity.mjs`：

```bash
node services/print-render/src/cross-end.parity.mjs <服务端 PDF> <客户端 PDF>
```

解析两份 Chromium 产物的明文 `MediaBox`，判定**页数与每页纸尺寸**是否一致。
客户端 PDF 需真机打印一次并在配置窗口开启「保留生成的 PDF」，因此不接入 CI 自动执行。
文字/条码位图不在自动判定范围内（字体残留差异），需要时人工目视比对。

### 3. 集成测试

- render 服务：`codes`/`continuous`/`subtotal` 等 integration test（真实起浏览器），
  不包含在根 `npm test` 中（根测试覆盖 core/canvas/client/print-client），由 CI 独立的 render job 执行；
- core：`print/__tests__`（pipeline、pdf-spec、units、dom-host-runtime、errors）
  与 `browser/__tests__` 覆盖管线逻辑本身。

## 五、接入约束（避免破坏一致性）

1. **字体同源**：模板使用的字体必须安装在实际出图环境——浏览器预览看用户系统；
   容器装中文字体（如 `fonts-noto-cjk`）；工位机安装到客户端系统。字体不仅影响换行，还影响条码宽度。
2. **内核版本**：要求严格像素一致时，让 render 服务与桌面客户端使用同一 Chromium 大版本；
   render 支持 `PLAYWRIGHT_CHROME_PATH` 指定内核。
3. **不要在宿主侧重写测量/分页/纸高/码制**：需要新能力时扩 core 并走架构守卫；
   自定义码制通过 `renderHtmlPages` 第 4 参数注入渲染器（覆盖语义），不要 fork 管线。
4. **纸张覆盖走逃生门**：普通纸型异常用 `paperOverride`，连续纸走纸公差用
   `paperHeightMm`（服务端）/ `paperSize.height`（μm，客户端），不要改模板数据。
5. **相对图片**：模板内 `/docfiles/...` 等相对路径必须通过 `baseUrl` 给出三端都能访问的基址。
6. **背景色/水印**：出图保留背景由 core 的 `print-color-adjust: exact` 与 PDF 规格保证；
   水印必须使用管线产出的显式矢量瓦片，不得改成 CSS 平铺背景（会被 PDF RIP 忽略图案矩阵）。

## 六、不一致排查顺序

1. **先比 MediaBox**：用 parity 脚本确认页数/纸尺寸是否一致。纸尺寸就不一致 →
   查纸张解析、方向、连续纸高度推导与逃生门参数。
2. **页数一致、某页内容位置不同** → 90% 是字体：核对三端字体安装情况与字体名。
3. **条码/二维码几何不同** → 确认三端用的是 core 同一码制算法（架构守卫可拦截第三方库直连），
   再查字体对文字宽度的影响。
4. **水印放大/错位/平铺错乱** → 确认没有用 CSS 平铺背景替换矢量瓦片。
5. **横向被打成纵向（仅客户端）** → 用 `pdfinfo` 看产物 `/Rotate`，查客户端日志下发的
   media 值；针式打印机有预置纸型时优先在宿主侧传 `paperName`。
6. **客户端彩色变黑白** → 配置窗口开「保留生成的 PDF」，PDF 正常则问题在打印机/驱动，
   与渲染一致性无关。
