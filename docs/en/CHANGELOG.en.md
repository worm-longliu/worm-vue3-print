## V1.4.1(2026-10-28)

### Fixed

- **Design-time barcode/QR values are no longer permanently masked by the sample value** (Gitee PR #1). The element factory presets a `testData` sample for barcode/QR elements, and it used to be resolved **before** the formatter — so once the author filled "content" with a `{field}` placeholder expression, the property panel and canvas kept showing the factory's placeholder code as if the content had no effect. All four design-time barcode/QR value paths (2 in canvas elements, 2 in the zero-framework print-common shell) now go through the single core helper `resolveBarcodeDesignValue`: `{field}` placeholders in the formatter are evaluated against sample data first (list fields take the data source's first item, global fields resolve by path — same rules as table cells), and the `testData` sample is used **only when the value cannot be resolved**. The helper gained a `fallback` parameter: table cells keep the generic sample value, element level passes `testData`/an empty string to preserve "testData only serves as a sample when the content yields no value". Regression tests cover the design-time live refresh. **Existing impact is design-time display only** — the print path still resolves live data via `resolveTextBinding`, so output, pagination and template contracts are unchanged; the desktop client's print behavior is unaffected and this release re-uploads the V1.4.0 installers.

## V1.4.0(2026-10-28)

### Added

- **Content rotation now works in tiling mode.** The template-level `outputRotation` used to be **forced to zero** whenever tiling was enabled (`getOutputPaperDimensions`, `getOutputRotationAngle` and `shouldApplyOutputRotation` all said "no output rotation in tiling"), and the property panel hid the row entirely — so "landscape design, portrait output" could not be expressed once labels were tiled. It now applies **per tile**: 0°/180° keep the grid geometry (content rotates/flips only); 90°/270° swap each tile's footprint (a 70×40 label becomes a 40×70 cell) and recompute max columns, rows and tiles per sheet from the swapped size, with the content rotated while staying unscaled and uncropped. Tiling geometry now takes `getOutputPaperDimensions` (the rotated output size) as the per-tile footprint and reuses the existing rotor layer inside each tile; `COLUMNS_OVERFLOW` / `LABEL_TOO_TALL` messages append "rotated N°, tile W×Hmm" so the rotated size is not mistaken for the design size. Both hosts keep the "content rotation" row visible with tiling on (hint switches to per-tile wording), and the tiling summary appends "tile W×Hmm". Switching between rotation tiers (0/180 ↔ 90/270) now also **auto-fills the tiling column count to the new tier's column cap** (switching back re-fills likewise; switching within a tier never rewrites, so a manually lowered count is preserved). Continuous paper still has no rotation concept.
  **Verified on real Chromium output** (A4 sheet / 70×40 label / 2mm gap): 90° at 4 columns → 40×70 tiles, 4×3 = 12 per sheet, tile origins left 10/52/94/136 and next row top 82, PDF text matrix rotated 90°; 90° at 2 columns → 6 per sheet, 12 copies span 2 sheets; 180° keeps the 0° grid and flips text 180°; 270° swaps the footprint like 90°. **No change for existing templates**: tiling templates without `outputRotation` produce byte-identical output (default 0°).
- **Per-element free-angle rotation.** Elements gained `options.rotate` (degrees, around the element centre, normalized to 0–359, unset = no rotation): pagination and paper-height derivation now settle on the rotated **axis-aligned box**, so an element that no longer fits moves to the next page and lands by its box top. Tables, flow lists and elements inside a table's follow region do not rotate in v1 — the property panel hides the "Rotation (°)" row and the canvas keeps them level (what you see is what prints). Barcode/QR free angles need a ≥385dpi head; below that they snap to 90° steps, and when the template declares no print head resolution the free-angle input is greyed out with only the ↺/↻ 90° step buttons left. Rendering uses the standalone CSS `rotate` property (never `transform`), so designer dragging and print output do not overwrite each other; a legacy `transform` key is ignored and output stays byte-identical. Measured: 100×20mm at 45° → box 84.85×84.85, top overflow 22.43mm reported as a warning, page-break landing renderTop=32.43; continuous paper at 30°/45° → 128.46/134.03mm; 90° PDF text matrix `[0,-9.9975,9.9975,0]` still vector; barcode at 203dpi/30° snaps to horizontal, at 600dpi passes through.
- **Print clipping warnings.** The pagination engine now emits per-page `PageLayout.warnings` when a rotated element's box crosses the page head, or when an element (rotated box included) exceeds the paper's left/right edge — "will be clipped on paper". **Advisory only**: `overflow` semantics and rendered HTML are untouched, and templates without overflow keep an empty `warnings` and byte-identical HTML. Two same-source entry points were added to core: `collectFollowMemberIds()` (the single table-follow-region judge shared by both hosts' property panel and canvas, which is what prevented "rotates on canvas, prints flat") and `collectPrintWarnings()` (an edit-time estimate that needs no browser measurement). Surfaced: a persistent "output notice" strip at the top of the Vue3 preview, one non-blocking notice when saving in both hosts, plus `getGeometryWarnings()` exposed by each for export paths; `renderInBrowser()` in all four zero-framework hosts now returns a `warnings` field. **Known gap**: the save-time check estimates heights from design boxes, so long-text/auto-height elements may warn conservatively — trust the preview layer's measured warnings.

### Changed

- **Print preview now defaults to 100%.** Templates that set `printerDpi` used to land on the "dots" preset (203dpi ≈ 2.11×, 300dpi ≈ 3.125×), and the rest on "fit", so the preview opened as an enlarged sheet. It now always starts at 100% (true CSS size, 1mm = 3.78 screen pixels); the five presets and the "dots" entry are untouched and still one click away. The trade-off is stated where it is visible: **thin barcodes still collapse at 100%** — a 95mm sheet is only 359 screen pixels, so a 297-module barcode face (74.32mm) squeezed onto 281 pixels gives each module 0.945 pixels. That is a screen limit, not a print defect: dot pitch on paper is settled by `printerDpi` in the render pipeline. Core gained `viewZoomHint(dpi, currentKey)`, which returns "条码看不清？切「点阵 Ndpi」档（1 屏幕像素 = 1 打印点）" whenever a template declares print-head resolution and a non-dots preset is active; the canvas preview and all four host replicas render it inside the preset bar, and it disappears once "dots" is selected. `defaultZoomKey` keeps its signature (the `dpi` parameter no longer participates, retained as part of the stable surface). **Printed output, pagination and the template contract are unchanged.**
- **`@worm-vue3-print/common` is now published as a regular version.** From 1.4.0 it shares the mainline version and publishes to `latest`, so `@next` is no longer required. The npm front page keeps the "experimental, not for production" notice and includes Vue 3 / Vue 2 / React integration examples (runnable projects under `demo-common/apps/{vue3,vue2,react}`). The earlier `1.4.0-beta.0` lived only on `next`; this regular release takes over `latest`.

### Fixed

- **QR codes ignored the print-head resolution gate when page and element rotation were combined.** The oblique-angle snapping in `resolveElementRotation()` only ever applied to `barcode`: all four call sites (render, pagination, both host canvases) hard-coded "pass `printerDpi` for barcodes only", so an oblique QR code printed as-is on a 203dpi station (jaggier modules, higher scan risk) while the field hint promised "barcode/QR snap automatically". The function now reads the element's own `printerDpi` (an explicitly passed resolution still wins, for output-side overrides) and none of the call sites re-implement the rule; the hint was rewritten to match measured behaviour (with no declared resolution the declared angle is used, hence the greyed-out input).
- **Side-by-side tight labels are no longer pushed to a second page by double-counted height.** The vertical pagination budget accumulates per "horizontally intersecting column": a QR code and an info row placed side by side each occupy a column, and the full-width row below them subtracts both column heights **twice**. The weight-tag / asset-tag / roll-label tight-size samples therefore spilled onto page 2, and tiling templates rejected them outright with "exactly one page per label". The side-by-side blocks in those three samples now share one `options.groupId` (explicit grouping keeps the group on one page and charges the union height once); grouping **does not change geometry**. The three samples, the four hosts' `templates.js` and both skill template assets were updated together, the `samples/index.ts` header convention gained "group side-by-side blocks", and the `print-template-json` skill documents the column rule and the grouping requirement. On the skill side `validate_template.py` gained `predict_pages`, which mirrors the engine's accounting (explicit groups and implicit clusters that intersect both ways collapse into one unit; continuous paper and templates containing tables / flow lists are skipped; >1 page in tiling is an ERROR, otherwise a WARN): all eight skill templates report 0 ERROR / 0 WARN, and removing `asset-tag`'s `groupId` immediately reports "tiling requires exactly one page per label, predicted 2". **Existing impact**: only templates that are side by side with a full-width element below and currently double-charge the budget go from 2 pages back to 1; templates without side-by-side blocks are unchanged.

## V1.3.11(2026-10-26)

### Added

- Text and long-text elements gained a **"保留换行符" (keep line breaks)** mode (`keepLineBreaks`, off by default) — from Gitee issue #IKPXQL request 2, "my text has indentation and line breaks, but they all print on one line". V1.3.10 fixed line breaks inside **table cells**; the **element** path was never supported: the default mode emitted no `white-space` at all, so the browser's `normal` collapsed hand-typed `\n`, leading spaces and repeated spaces into a single line — while the property panel's expression preview is `white-space: pre-wrap`, which is why the break looked fine in the panel and vanished on canvas and paper. Once the mode is on, output carries `white-space:pre-wrap`: every `\n` starts a line, leading and repeated spaces survive, and the text still wraps at the box width. When "auto wrap" is off, **single line wins** (the mode emits nothing).
  The decision lives in one place — core `resolveElementWhiteSpace` (`render/text-fit.ts`, exported via `/designer`) — and all three renderers consume it: `html-generator` for output, canvas `TextElement`/`LongTextElement`, and print-common `textLikeStyle`. It is deliberately **not** placed inside `elementFitStyle`: long text defaults to the `autoHeight` display mode, and that function returns early on that branch, so a declaration put there is swallowed outright. A test pins this (moving the declaration into `elementFitStyle` leaves `text` green while both `longText` assertions go red — verified). Each shell gained one row directly under "auto wrap" with the same label and position; switch rows keep the house convention of **no help bubble on either side** (so the registry never holds copy nobody reads), and the reset-to-default icon greys at factory state (unset). New registry key `ap-keep-line-breaks`, searchable by several phrasings, with two-way negative controls against "auto wrap".
  **Existing templates and all three print paths are byte-for-byte unchanged**: the key is neither written by `createDefaultOptions` nor emitted unless the user turns it on. That is a measurement, not an inference — the real two-pass pipeline (Chromium measure → pagination → final HTML) was run over **27 documents** (11 renderable demo samples + 15 element-mode combinations + 1 cell matrix) before and after, all identical; two tiling samples could not be rendered by that offline harness and are excluded as a stated limitation. Behaviour changes only when the mode is switched on (extra lines grow the element and can move pagination), so this counts as **minor**. `docs/中文/指南/使用指南.md` and the `print-template-json` skill's `references/template-schema.md` were updated — the skill's previous claim that "`\n` works when `wordWrap` defaults to true" only held for cells and has been corrected.
- **New demo sample "文本换行与跟随示例"** (samples 13 → **14**): one A4 template that demonstrates all four V1.3.11 paper rules at once — multi-line text via "保留换行符", the single-line overflow of auto-wrap off, the 1.5x default line height of long text, and an element placed beside a table that no longer gets dragged along by the follow region. The previous 13 samples covered **none** of these combinations, so the new capability was invisible in the demo and untestable by `verify-demo`; nine assertions were added across the four hosts (canvas `white-space` / `line-height` parity and measured line counts/heights on paper, plus three structural ones — the static table renders all 4 rows, a `flow-follow` follow region exists, and the beside-table element stays absolutely positioned outside it), taking `verify-demo` from 42 to **51**. Each host's `templates.js` was regenerated via `npm run samples:demo-common`. Two asset defects were caught live while landing the sample and fixed on the spot: without `unit: 'mm'` the element coordinates were scaled as pt while column widths/row heights were not, so the table's design bottom swallowed the elements below and the follow-region check found nothing; and without `tableMode: 'static'` the data rows of a data-less table vanish, leaving only the header row on paper — the three structural assertions were all red before the fix and 51/51 green across the four hosts after.

### Fixed

- **Vertical lines inside a table's follow region printed with zero height (they vanished)** (ledger T-11 C1, same root issue as Gitee #IKPXQL). Follow-region members only get their design height written into the inline style when `html-generator`'s `needsHeight` allows it, and that check recognised `rect`/`oval`/`image` alone — while `case 'vline'` emits just `border-left` + `width:0` and takes its length entirely from the incoming `height`. A vertical line below a table was therefore visible on the canvas and 0 mm tall on paper. `vline` is now part of the check. **`hline` was deliberately left alone** — its `height:0` is intentional (length comes from `width`) — and a negative-control case pins "follow-region hline still emits no `height`", while positive controls pin `rect`/`oval`/`image` behaviour so the existing tiers cannot be displaced. Real-Chromium measurement inside the same follow container (a 14 mm vline plus an 80 mm hline as control): before, the vline painted at **0 px** (absent from the sheet) while the hline was a normal 1 px × 302.36 px; after, the vline paints at **52.91 px = 14 mm** exactly and the hline is unchanged value for value (80 mm × 1 px) — which confirms both the defect and the "leave hline alone" boundary. **Existing impact**: only templates that place a vertical line in a table's follow region change, from "not printed at all" to "printed at design length".
- **Turning off "自动换行" (auto wrap) on a long text had no effect on paper** (ledger T-27, an existing divergence this round surfaced). `text` with `wordWrap:false` printed `white-space:nowrap;text-overflow:ellipsis;`, `longText` printed only `overflow:visible;`. Root cause: `elementFitStyle()` returns early in the `fit === 'autoHeight'` branch, and `autoHeight` is exactly the default display form of `longText`, so the nowrap line was unreachable; both the canvas and print-common attach `nowrap` + ellipsis when `wordWrap === false`, i.e. **single line with ellipsis in the designer, still wrapped on paper**. The two declarations are now concatenated (`overflow:visible;` alongside `nowrap`, character-for-character the same shape as the canvas), restoring three-way parity. **Existing impact (visible behaviour change, counted as minor)**: any text/long-text that turns off auto wrap without an explicit overflow form now prints as a single line instead of wrapped; the measured height of `autoHeight` shrinks from N lines to 1. **Pagination does not move** (the earlier draft's "can move pagination" is retracted, disproved on the real two-pass pipeline): with the element placed so its content bottom overshoots the content area by 3 mm, both settings still land on the same page — standalone elements are assigned by `top`, and the `flow-follow` container height uses design geometry, not measured values. Byte-level comparison bounds the surface: of 31 artifacts (13 demo samples + 15 element option combinations + 4 follow-region shapes) **25 are identical**, the differences are exactly the added declaration and only land on the five `wordWrap:false` + `autoHeight` combinations, and all 13 demo samples are unchanged (none uses that combination). The trigger condition must be stated in the docs at release. Real-Chromium line-box probe (same 60 mm-wide element, 78 characters, `lineHeight: 5pt`): before, `white-space:normal` → **4 lines**, element height 26.69 px; after, `white-space:nowrap` → **1 line**, element height 6.67 px with `scrollWidth` 816 px overflowing the 226.77 px box. **Stated honestly**: `autoHeight` keeps `overflow:visible`, and an ellipsis can only be drawn inside a clipped container, so this combination prints as a **single overflowing line** (no wrap, no "…" truncation) — the same shape the canvas shows; pick "截断" explicitly when an ellipsis is wanted. Documentation backfill: the `textFit` table section in `docs/中文/指南/模板设计器.md` and the `wordWrap` row in the `print-template-json/references/template-schema.md` skill both carry this boundary now, including the "not effective up to V1.3.10" version caveat and the judgement command. **No conflict with "保留换行符"**: when both are on, single line wins (the decision still returns `undefined`), pinned by cases with controls.
- **npm's `latest` for `@worm-vue3-print/common` points at the preview build** (ledger T-15). `npm publish --tag next` only constrains the tag written by that publish; it cannot stop npm from stamping `latest` on a package's very first publish. Live registry check shows `latest` and `next` both at `1.3.7-beta.0`, so a host running `npm i @worm-vue3-print/common` without `@next` gets **no error — it silently installs the experimental package**, the opposite of the package's stated status. Three doc surfaces (root README, package README, integration skill) previously claimed "`latest` does not exist yet, omitting `@next` fails with `No matching version found`", which is not what the registry says; those claims are corrected against the measurement. A new exit-code-graded self-check `scripts/check-common-dist-tag.mjs` was added (0 healthy / 1 red with the repair command / 2 unreadable) and wired into `publish:common:beta` (runs `--fix` after publishing, removing `latest`) and `publish:common:dry-run` (`--dry-run`, reports without mutating); run it standalone via `npm run publish:common:check`. **Actually removing the tag still requires the maintainer's local npm login** — the repo side now carries the judgement and the pathway.

- **Default line height of long text now matches the designer** (ledger T-28). With no explicit `lineHeight`, the canvas and print-common have always laid out `longText` at **1.5x**, while the sheet fell back to the browser default (about 1.2x) - the same multi-line paragraph printed about 9% shorter than designed (measured 24 px vs 22 px per line at 12 pt / 60 mm). Paper now emits `line-height:1.5` (unitless, never overriding an explicit pt value). **Existing impact (visible change, counted as minor)**: every long text without an explicit line height gets looser leading - `autoHeight` elements grow, `clip`/`shrink` forms show one line fewer. Of 29 artifacts **25 are byte-identical**; the only diffs are the four "longText without lineHeight" combinations, one added declaration each; **all 13 demo samples and 8 skill templates are unchanged** (no long text there omits line height - the 85 elements missing it are all `text`, already `normal` on all three ends). Real Chromium re-check: 22 px to 24 px per line, equal to the canvas.

- **Elements beside a table are no longer dragged away by the follow region** (ledger T-11 C2, same root as Gitee #IKOUJI). The follow rule only looked at `top >= table design bottom` and **ignored the X axis entirely**, so an element in a column to the right of the table — or one far away horizontally — was absorbed and drifted with the table's real bottom (measured 78.53 mm off historically). Now **only elements that horizontally intersect the table follow it**; zero-overlap elements keep their absolute position, while elements directly below in the same column still follow. **Existing impact**: byte-level comparison of **20 artifacts** (13 demo samples + 8 skill templates) is **identical in every case** (their follow members all intersect the table; zero-overlap members measured across assets = 0); only user templates that place another column beside a table change.

## V1.3.10(2026-10-24)

### Added

- New **flow list element `flowList`** (from GitHub issue #5 — a traditional-Chinese-medicine prescription that lays 7–11 herb entries out as "name dose" pairs, four per row, wrapping when the row is full; a table can't express borderless column slots, and long text only breaks at arbitrary characters, splitting a drug name in half). The author sets **columns per row, row height and horizontal gap** with steppers (columns are never auto-computed); each item's content is one **expression template** (`{name} {spec}`) evaluated per array entry, sharing the table's list-source resolution. Two new capabilities: **auto span** (off by default — an item wider than one column takes two or more column slots, and if the current row has no room the whole item moves to the start of the next row, so words are never split) with a **max span** ceiling that is **clamped to the column count** (the only place in this feature that rewrites a user-entered value). When the chosen column count no longer fits the box, the panel **only hints and never writes back** (same convention as the barcode recommended bar-width). **One box, one page**: content beyond the box height follows the existing `textFit` modes (default `clip`) — no pagination-engine involvement; use a table when you need continuation across pages. **Spanning only takes effect on output**: the design canvas runs neither the measurement pass nor pagination, so it always shows one cell per column and the preview / print result is authoritative. Implementation: new core module `render/flow-list.ts` (defaults, clamping, width estimation, slot layout — pure logic without DOM, one source for all three output paths and both shells), `data-binder` now lets non-table elements consume arrays, `html-generator` emits a CSS Grid (`grid-auto-rows:minmax(rowHeight,auto)` for the min-height semantics, `grid-column:span` for spans), plus `element-factory` / `binding-registry` / `property-search` (including tip copy); the Vue 3 shell gains `FlowListElement.vue` and a "流式列表" property group, and print-common mirrors the same class names and toolbox order. **Existing templates are unchanged** — nothing is emitted unless the new element is used. A new demo sample **"中药处方笺"** (A5 portrait, 11 herbs, two carrying preparation notes) was measured on output: 4 rows, both long items occupy 2 column slots, every row fills 4/4 slots, 4 rows × 8 mm equals the 32 mm box height, single page; the four demo-common hosts' `templates.js` were regenerated (sample count 12 → **13**).

- Every property row in the panel that **has a factory default** now carries a reset-to-default icon at the right end of its label (`RotateCcw`, the same lucide source as the top toolbar, identical in both the canvas and print-common shells). One click writes that row back to **its own layer's factory value**: element options return to `createDefaultOptions(type)`, table-level defaults to a freshly created table, cell options clear themselves so the value follows the table default again, watermark/tiling/page background return to their constants. The icon is always present but **only lights up when the current value differs from the factory value**; when already at default it is greyed and clicking records no history entry. The tooltip states the target directly ("恢复默认值（12 pt）", or "跟随表格默认" for cell rows). **Per row only — there is no group-wide or element-wide reset.** The page background's old "默认" text button was folded into the same icon slot. Landing: new `property/ResetButton.vue` in canvas (75 rows in each shell: appearance 14, crop anchor + fit-scale 2, code 11, advanced 3, table settings 4, cells 24, border & background 3, watermark 5, tiling 8 incl. 4 sheet margins, page background 1), a 4th `reset` argument plus a `resetButton` primitive in print-common's `controls.ts`, styles and icons re-derived from the canvas build output.

  **No new default-value storage**: the reset target is derived from the layer's factory value at click time. The `default`/`defaultUnit` fields added to `PROPERTY_REGISTRY` **only feed the tooltip text and are never read by behaviour** — so registry/render-constant drift can mis-word a tooltip but can never reset to the wrong value. Render-side truth references the constants rather than copying them (`DEFAULT_SHRINK_MIN_FONT_SIZE_PT` / `CROP_SCALE_MIN` / `BARCODE_QUIET_ZONE_MODULES` / `BARCODE_BAR_HEIGHT_MODULES` / `BARCODE_TEXT_FONT_SIZE_MODULES` / `QR_DEFAULT_QUIET_MODULES`; the last moved from `browser/` into the isomorphic `render/barcode-dot.ts`, since the designer must not depend on the jsbarcode-bearing browser layer). Core's `reset-default-parity.test.ts` guards it: after a reset the options equal a freshly created element key by key, and every positive assertion is paired with a negative control (three of the original thirteen were false greens exposed only by it). barcode / qrcode / table carry no discriminating power at the `generateHtml` layer, so they assert at the options and settlement layer instead, with real paper covered by the render-service regression. **Existing templates and all three print paths are unchanged**: nothing is written unless the icon is clicked.

- Two new **battery module label** samples in the demo library (95×75 mm single label, four-column grid as the whole layout): "电池模块标签（含 SN 条码）" (the "SN" caption cell takes column 1, the barcode cell spans columns 2–4) and "电池模块标签（无 SN 标签格）" (barcode kept, the "SN" caption cell dropped and the barcode cell merged across the full row). The two differ only in how the SN row is divided, which makes them a clean A/B pair. Taken from a real exported business template with three adjustments: no font is set (the source template's Heiti is dropped, see "取消字体预置" below — paper falls back to the render target's default font), the SN barcode set to **bar-width multiplier 3 + bar height 7 mm + 203 dpi** (the source template had multiplier 2, no bar height, 600 dpi), and the table element height corrected to the sum of row heights (the sample-library hard rule: column widths sum = element width, row heights sum = element height, cells per row = columns). The library grows from 10 to **12** samples and the four demo-common hosts' `templates.js` were regenerated. Content is all static text (no `{field}` placeholders), so these two samples carry an empty field tree and print data.

- Once a **printer resolution is chosen**, the property panel shows a **recommended bar-width multiplier plus the current conversion** under "条宽（倍率）" — as a hint only, it **never writes `barWidth`**. Rule: the smallest multiplier whose snapped module width reaches 0.254 mm (the commonly cited 10-mil floor) — **203 dpi → 3** (3 dots / 0.375 mm), **300 and 600 dpi → 2** (already 0.254 mm after snapping). No recommendation without a resolution (nothing to snap to). The text also reports the current setting: the default multiplier 2 at 203 dpi is only 2 dots / 0.250 mm and is flagged as below the floor. Half steps often snap onto the same dot count (at 203 dpi, 2 and 2.5 are both 2 dots), so a recommendation never pretends a half step is thicker. Single source: `recommendBarcodeBarWidth` / `barcodeBarWidthRecommendText` in core, shared by the canvas element and cell panels and both print-common panels. **Existing templates and print output are unchanged** (the text lives only in the hint).

- Table cell borders gained a **how-to-apply hint**: line style / width / colour are only a **pending draft** — they reach the selected cells once you click 全部 / 外侧 / 内部 or tick one of the 上 / 右 / 下 / 左 edges (无 clears them). The canvas and print-common cell panels both show this line under the preset and edge rows, with the copy kept once in core as `CELL_BORDER_APPLY_HINT` (next to `applyBorderPreset`) so the two hosts can't drift. **Hint only, no behaviour change**: draft semantics and all print paths untouched.

- The element panel's **Borders & background** now matches the table-cell panel: a 线型 (line style) dropdown plus 全部 / 外侧 / 内部 / 无 presets and 上 / 右 / 下 / 左 single-edge ticks. Presets and single edges appear only for types where `acceptsElementBorder` holds — rect / oval / hline / vline / table draw their own stroke, so writing per-side borders there would do nothing. **内部 stays disabled for elements** (an element has a single ring of edges, no shared inner lines), same rule the toolbar already applies, with the reason in the permanent hint line rather than a hover. The element panel deliberately does **not** copy the cell panel's draft-then-apply: an element's own `borderWidth/borderStyle/borderColor` *are* the spec, so those fields take effect immediately and presets/edges just spread the current spec; a zero width falls back to `0.75pt` so 全部 never no-ops, while 无 zeroes only the width and keeps style/colour. - Linux installers for the desktop client (`deb` / `rpm` / `AppImage`, x64): `npm run pack:client:linux` cross-builds them inside a Docker container (the `rpm` target needs `rpmbuild`, which macOS does not have), and the artifacts are attached to the release. Payload, declared dependencies and SHA-256 are verified, but **no installation or printing on real Linux hardware has been tested**: printing relies on CUPS, the AppImage needs `libfuse2` (or `--appimage-extract-and-run` on fuse3-only distributions), and `chrome-sandbox` inside the deb/rpm is not setuid (`0755`). No `snap` and no arm64 builds in this release. See the [client README](../../clients/print-client/README.md).

### Fixed

- Desktop client (Windows): **silent printing rotated wide label pages 90°**. A 100×75 mm label came out a quarter turn off even though the generated PDF is correct in any viewer. Windows output is handed to SumatraPDF, whose default `autoRotate` unconditionally adds 90° to pages where width > height and cancels it back to 0° only when the page is judged landscape — with no orientation declared, that judgement comes from the print driver (label drivers usually report portrait). The client now declares the orientation from the page's own aspect ratio (`-print-settings "<copies>x,landscape|portrait"`, square pages counted as `portrait`). **Behavior change**: the same wide label now prints in the orientation the PDF shows; templates turned sideways to work around the old behavior must go back to their real output orientation. If the label definition in the driver disagrees with the template, the driver can still rotate the output back — align the driver / machine setting.
- Desktop client (macOS / Linux): **the paper declaration was never actually sent**. `printPdfFile` forwarded options field by field and dropped `paper`, so the page size never reached argument construction and the `-o media=…` declaration (host driver paper name → standard-size match → `Custom.<w>x<h>`) introduced in V1.3.0 only went out when the host supplied a driver paper name. All options are now passed through unchanged. **Behavior change**: macOS / Linux output now really declares the paper, so jobs that previously fell back to the queue's default paper (usually portrait A4/Letter) use the page's true size; landscape pages also need the orientation declaration in the next entry.
- Desktop client (macOS / Linux): **declaring a paper name alone did not stop landscape pages from rotating**. Measured on a real queue, the trigger is the same as on Windows — CUPS' `pdftops` adds 90° whenever the effective media's orientation disagrees with the page's, and standard names such as `A4` / `Letter` are **portrait media** by definition, so declaring one pins a landscape page onto a portrait sheet and it gets rotated anyway. On macOS the output command now also sends `-o orientation-requested=4` when the page is wider than tall and no driver paper name was given, which makes the filter swap the media to landscape (`do_rotate` measured 90 → 0); it is never sent for portrait or square pages, because there it flips the media the wrong way and rotates correctly oriented content instead. Since that request swaps the media's dimensions, `Custom.` sizes are now declared **portrait-canonical (short side × long side)** on macOS so one swap lands exactly on the page's real size (measured on a custom-size-capable queue: declaring the true order and then swapping turned a 100×75 label back into 212.6×283.46). **Linux takes the paper route instead**: cups-filters 1.28 implements `orientation-requested` by writing `/Rotate 270` into the page and swapping the MediaBox, which skews label output, so Linux skips that request and stops reporting portrait paper names for landscape pages, declaring `Custom.<width>x<height>` in the page's real orientation (A/B measured on a custom-size-capable queue: MediaBox went from 595×842 to 841.89×595.28 with no `/Rotate`). **Behavior change**: landscape A4 and wide custom paper now print in the orientation the PDF shows on both macOS and Linux. Note that queues whose PPD has no custom-size support **silently ignore** `media=Custom.*` and fall back to the queue's default paper (AirPrint / driverless queues do this — all three option sets measured identically rotated); for label stock, pass a `paperName` the driver already defines.

  ② binary float noise is removed — `0.1 + 0.2` was `0.30000000000000004`, now `0.3`; `12.5 * 3 * 1.13` was `42.37499999999999`, now `42.375`;

### Fixed

- `ROUND(n, d)` was implemented with `Number.toFixed`, producing wrong results on float boundaries: `ROUND(1.005, 2)` returned `1` (should be `1.01`) and `ROUND(2.675, 2)` returned `2.67` (should be `2.68`). Rounding is now exact in decimal.
- `@worm-vue3-print/core` / `@worm-vue3-print/canvas`: system variables could not be used **inside** an expression — `{pageIndex + 1}`, `{ADD(pageIndex,1)}` and `{DATE(printDate,'YYYY')}` failed to evaluate and were printed verbatim (the template fallback for failed evaluation); only a bare `{pageIndex}` worked, via a text substitution applied after rendering. Cause: the binding-time expression context contained business data only, and page numbers are unknown until pagination. Now: ① `printDate` / `printTime` are merged into the binding context (business data of the same name wins); ② expressions referencing `pageIndex` / `totalPages` keep their source text at binding time (measurement pass measures the raw text) and are re-evaluated per page during final rendering — consistently for elements, header/footer, first-page overlay and table cells, and identically across browser preview, server-side PDF and the desktop client. **Output for existing templates is unchanged**: templates without any raw formatter take a fast path with no re-evaluation.
- `@worm-vue3-print/core` / `@worm-vue3-print/canvas`: **multi-level table headers lost every level below the first on continuation pages**. The rows of a multi-level header form a single structure through `rowspan` / `colspan`, but "repeat on every page" was decided per row: with only the first header row checked, continuation pages repeated just that row and dropped all levels below it, and the row-spanning master cell could overrun and swallow the position of the data rows. Now: ① if any row in the header zone (the consecutive header rows starting at row 0) is checked, the **whole header zone** repeats; ② the repeat count is aligned to the nearest `rowspan`-closed boundary, and a master cell overrunning the header zone is clamped during continuation rendering so it can no longer swallow data rows; ③ inserting a header row or changing a row type to header inherits the neighbouring header row's setting, so a missed checkbox cannot break the structure; ④ the property-panel switch is renamed "表头每页重复" and applies to the whole header zone. Single-row headers behave exactly as before, and existing single-row-header templates render byte-identically.

  no longer stretch to fill their box. All ends now settle the size through one shared algorithm
  (`resolveBarcodeSize` in `render/barcode-dot.ts`): ① **preferred size comes from the bar width** — one module is
  `barWidth/2 × 0.25mm`; when the box is wide enough the barcode prints at that size instead of being scaled up
  (scaling up is exactly what produced non-integer module widths, i.e. the "bars alternate between 2 and 3 dots"
  artifact); ② **when a printer resolution is set, dpi wins** — the preferred size snaps to an integer number of
  printer dots per module (dpi takes priority over the exact millimetre value, e.g. 0.25mm becomes 3 dots ≈ 0.254mm
  at 300dpi); ③ **when the box is too narrow the barcode shrinks proportionally** — in integer-dot steps while the dot
  grid holds, and only falls back to continuous scaling when even one dot per module does not fit (then dot alignment
  is impossible, but the barcode still never overflows the box). Width and height always scale together, so the
  barcode is never distorted. Designer canvas, browser output and the render service share the same constants and
  algorithm for elements and cells alike; barcode output is now **always inlined as `<svg>`** (Chromium rounds the
  intrinsic size of an `<img>`-hosted SVG to whole CSS pixels, which rewrote the settled millimetre size), and
  `maxWidth` / `maxHeight` are folded into the available box. Because stretching breaks integer module widths, the
  "缩放模式" (fit) option is **removed for barcodes** — use the bar width to change size and "最大宽高" to cap it.
  **Existing templates will print smaller barcodes** (about half the element box with the default `barWidth: 2`);
  that is intentional — raise the bar width to grow them and get stable bar widths on paper.
- `@worm-vue3-print/core` / `@worm-vue3-print/canvas`: text elements and table cells now support **three text-overflow
  display modes** (property panel "文字溢出", template field `textFit`): `clip` (truncate; single-line ellipsis when
  `wordWrap: false`), `shrink` (auto-shrink down to `shrinkMinFontSize`, default 6pt, falling back to truncation if it
  still overflows) and `autoHeight` (element height / row height grows with the content). **Defaults keep existing

### Added

- `@worm-vue3-print/core`: Added **barcode print-dot alignment** (new module `render/barcode-dot.ts`) — the barcode's final size is snapped to the printer's dot grid, fixing "bars come out alternately wide/narrow with gray edges" on thermal printers. Root cause (measured): with a 56.4×14.1 mm element box and an 8-digit CODE128, one module is 0.318 mm, i.e. **2.55 dots at 203 dpi (8 dots/mm)**. The barcode is pure vector and geometrically exact in the PDF, but the printer/RIP can only image whole dots, so a fractional module width is rounded to 2 or 3 dots per bar. Dedicated label tools look crisp because they define the narrow bar as a whole number of dots (e.g. 3 dots = 0.375 mm). Barcode elements accept `printerDpi` (`options.printerDpi`, typically 203/300/600), and **barcode table cells accept it too** (`TableCell.printerDpi`; the box is the cell's content area — spanned column widths / row heights minus padding and collapsed borders, derived with the new `cellFitWidthMm` plus the existing `cellFitCapMm`; when a table has no `tableColWidths` the width is unknown and alignment is skipped). Both surfaces expose a "Printer DPI" dropdown and hide scaling mode / max width / height while dot alignment is on (stacking them would rescale the aligned size back into fractional dots); switching a cell away from barcode clears the field. Two other clarity culprits were fixed as well: ① barcodes now set `shape-rendering="crispEdges"` (QR codes always did; measured gray-edge pixels drop from 11.3% to 1.7% of the ink); ② **left/right quiet zones are restored** (jsbarcode's default 10 modules was overridden with `margin:0`, which made EAN13/UPC/ITF14 unscannable) — and only left/right, so vertical whitespace no longer eats the element height. ### Fixed

- Print client: Fixed the silent-print failure chain "PDF generation timeout → every later job returns BUSY". `webContents.printToPDF` no longer accepts a callback (the callback never fires and the returned promise rejection is swallowed), and `PrintToPDFOptions.pageSize` is in **inches**, not microns (passing microns produced a 210000×297000 inch page, which Electron 44 refuses to generate). The client now uses the promise form with a timeout guard (`src/main/pdf-generator.ts`), converts microns to inches, sets explicit zero margins and `printBackground: true`, and reports generation failures/timeouts as `PRINT_FAILED` while always releasing the serial gate. Printed output now matches the server-side PDF in paper size and watermark rendering.
- Print client: Documentation now describes the "HTML → printToPDF → system print command" pipeline (`clients/print-client/README.md`, Chinese silent-print guide, silent-print skill reference).
- `@worm-vue3-print/core`: Fixed watermarks being magnified ~3x, offset, and tiled incorrectly when printing to paper. The watermark used to be a CSS tile-repeated background (`background-image` + `background-repeat`), which Chromium compiles into a PDF tiling pattern; PDF viewers render it correctly, but the print path RIP ignores the pattern matrix (the enclosing form had a CTM of 3.125 = 300dpi÷96px, matching the measured magnification). Watermarks are now explicit vector tiles: `resolveWatermarkLayout` computes the tile grid for the final paper size (including the probed continuous-paper height) and emits one inline `<svg>` per tile, restoring the designed geometry on paper (68.8mm × 47.6mm at default A4 density). `buildWatermarkSvgDataUrl` was removed to prevent regressions back to the tile-repeated background approach.
- Print client: Fixed the printed page orientation not matching the browser/server preview (landscape pages came out portrait). The print command did not declare a paper size, so CUPS used the queue default sheet (usually portrait A4) and `pdftopdf` rotated landscape pages by 90° (the resulting PDF carried `/Rotate 90`). The client now sends an explicit `-o media=…` (host-provided driver paper form → matched standard size → `Custom.<width>x<height>` in points). Verified: the same landscape A4 page went from `/Rotate 90` back to `/Rotate 0`, and portrait pages are unaffected.
- `@worm-vue3-print/core`: Fixed a **blank first page** on small-paper templates (e.g. an 80×60mm custom sheet with 10mm margins and 38mm of content). Two root causes: ① `finishPage()` pushed the current page unconditionally, so when the very first element/unit did not fit it emitted an empty sheet and pushed all content to the next page. Empty pages are no longer emitted — the content stays on the page at its designed coordinates. `PageLayout.overflow` now records "content bottom exceeds the content area and would be clipped by the sheet", judged against the physical content height rather than the pagination budget's 2mm safety margin (content sitting close to the paper edge is still valid layout), so the tiling check ("each label must be exactly 1 page") keeps blocking only genuinely over-tall content. ② The DOM executor measured element height with `offsetHeight` (integer px, rounded up): 38mm was read as 144px = 38.1mm, which crossed the 38mm budget (40mm content area minus the 2mm safety margin) and made fitting content look oversized. It now reads `getBoundingClientRect().height` for true sub-pixel height (table row heights included).
- `@worm-vue3-print/canvas`: Fixed drifting page names and duplicate names on new pages in multi-page templates. The first page (created by the default template or loaded by the host) stored no `name`, so tabs fell back to "页面 N" computed from the index; moving a page shifted the fallback and clashed with the names already persisted. Unnamed pages now get a fixed default name at load, and `addPage` picks the first unused one (so adding after deleting can no longer collide).
- `@worm-vue3-print/core`: Fixed missing **page breaks between copies** in multi-page batch printing. Each copy was wrapped in `.print-copy`, but the composed CSS omitted the copy-break rule, so the last `.print-page` of a copy matched `:last-child` (`break-after: auto`) and two copies ran together. `COPY_BREAK_CSS` is now exported and appended when batching, and a render integration test asserts "2 copies × 3 pages = 6 pages".
- `@worm-vue3-print/core`: The browser adapter `renderHtmlPages` (`@worm-vue3-print/core/browser`) now accepts `TemplateData | MultiPageTemplateData` (and an array `printData`), so multi-page templates can be rendered in the browser directly.
