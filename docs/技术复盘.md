# 技术复盘

> 本页记录开发过程中踩过的坑与结论，偏内部经验沉淀。对外机制说明以
> `docs/中文/指南/` 下文档为准。

## 技术方案原则

- 三端通用的代码全部抽离到核心包（`@worm-vue3-print/core`），各端只保留宿主 I/O 适配。
- 技术实现需要使用已有方案（成熟库/平台原生能力），不自行发明轮子。
- 同源边界用工具强制：`scripts/check-print-architecture.mjs` 禁止三端重复实现
  测量、纸高推导、出图参数与码制渲染，架构守卫不过即视为破坏一致性。

## HTML 打印设计与打印结果出现偏差的原因

1. **字体不同源（最常见）**：预览、服务端容器、工位客户端任一环境缺少模板所用字体，
   文字度量变化会改变换行，进而改变每页元素数量与分页位置。容器环境需安装中文字体
   （如 `fonts-noto-cjk`），工位机需安装到客户端系统。
2. **浏览器内核版本差异**：三端都是 Chromium 系（浏览器 / Playwright Chromium / Electron），
   但大版本不同仍可能有排版细微差异。要求像素级一致时锁定同一大版本
   （render 服务可用 `PLAYWRIGHT_CHROME_PATH` 指定内核）。
3. **字体宽度会传导到条码**：条形码元素宽度取 `ceil(max(文字宽, 条码宽))`，
   字体不同不仅影响文字，还会改变条码 SVG 的固有宽度，导致条码在框内尺寸不一致。
4. **资源就绪时机**：字体与图片未加载完成就测量，会得到偏小的高度，导致分页错误。
   管线统一在测量前执行就绪等待（`waitReady`，默认 5s 预算），不再允许各端各自写等待策略。
5. **背景色丢失**：Chromium 打印默认不输出背景，必须由 core 统一在 CSS 中声明
   `print-color-adjust: exact`，并在 PDF 规格中开启背景打印（driver 只透传，不自行设置）。
6. **水印不能用 CSS 平铺背景**：CSS 背景图案会被 Chromium 编译进 PDF 的图案矩阵，
   部分打印机 RIP 会忽略该矩阵，表现为水印被放大、错位或平铺错乱。
   结论：水印必须以「显式矢量瓦片」渲染（每块一个 `<svg class="watermark-tile">`）。
7. **分页认知偏差**：屏幕上看到的是设计画布，真正分页以真实浏览器文档中的实测高度为准；
   连续纸设计画布固定 297mm 高只是设计态，实际出纸高度由内容探针推导。

## 放大缩小偏移问题

1. **以毫米为唯一布局基准**：模板坐标全部使用 mm（旧 pt 数据加载时自动迁移），
   不使用屏幕 px 作为存储单位，避免 DPI/缩放下漂移。
2. **px↔mm 换算只认 core 常量**：换算常量与函数集中在 core——
   `print/units.ts`（`PX_PER_MM`、`pxToMm/mmToPx`、mm↔μm、mm↔英寸等，打印管线统一使用）
   与 `render/watermark.ts` 导出的 `PX_PER_MM` / `MM_PER_PX`（渲染/水印使用，数值同为 96/25.4）；
   各端不得自行取 `devicePixelRatio` 推算或另写换算。
3. **视口按目标纸张推导**：driver 打开页面时使用 `paperViewportPx(paperMm)` 得到的
   CSS px 视口，保证测量文档与最终纸张同宽，两趟渲染使用同一视口。
4. **禁止 driver 侧缩放参数**：出 PDF 时 `printBackground`、`preferCSSPageSize`
   等参数只能由 core 的 `pdf-spec` 推导（架构守卫对这些字段做了禁止扫描），
   避免某一端偷偷加缩放导致与其它端偏移。
5. **排查方法**：先用 `cross-end.parity.mjs` 比对 MediaBox（页数与纸尺寸），
   MediaBox 一致但内容偏移，优先查字体；MediaBox 就不一致，查纸型/方向/连续纸高度。

## 桌面客户端技术选型

- **选型：Electron。** 关键理由是内嵌 Chromium：与浏览器预览、Playwright 服务端同属
  Chromium 内核，同构管线产出的 HTML 在三端排版行为最接近；同时 Electron 提供
  `webContents.printToPDF` / `webContents.print` 的静默出纸能力，无需系统打印对话框、
  不依赖浏览器插件，且 Windows/macOS/Linux 三端一套代码。
- **进程分层**：主进程（WebSocket 服务、打印引擎、打印机服务、配置与任务记录）、
  隐藏渲染 worker（core 同构渲染）、preload（沙箱 IPC 桥）、配置窗口（Vue 3 renderer）、
  shared（IPC 通道契约）。
- **通讯**：仅绑定 `127.0.0.1`，默认端口 17521（占用向后探测），SDK 自动端口探测、
  指数退避重连；安全开关默认关闭（开箱即用），开启后需配对 token 并校验 Origin。
- **任务模型**：客户端串行执行打印（不排队，忙碌返回 `BUSY` 由宿主决定重试/入队），
  配置与任务记录本地化，业务打印配置（打印机/份数/纸型）由宿主维护下发。
- **不采用的路线**：浏览器直连系统打印机（必然弹原生对话框、各浏览器 API 不统一）、
  本地常驻 HTTP 代理（跨平台安装与防火墙成本高于 Electron 安装包）。

## 桌面客户端打印

- 出纸链路：core 管线产出最终 HTML 与 PDF 目标规格 → `driver-electron` 调
  `printToPDF`（mm→英寸映射由 core 的 `toElectronPrintToPdfOptions` 完成）
  → `pdf-printer` 调系统打印命令出纸。`pdf-printer.ts` 是唯一允许出现出纸命令的文件
  （架构守卫白名单）。
- **纸张声明**：客户端显式向打印系统声明 media，优先级为
  宿主指定纸型名（`paperName`，针式优先）> 标准纸型匹配 > `Custom.<宽>x<高>`。
  横向被打成纵向时，用 `pdfinfo` 查产物 `/Rotate`，并在日志核对下发的 media 值。
- **连续纸**：纸高由浏览器探针推导（动态表格/签名区都计入），真机走纸公差不满足时，
  宿主可显式下发 `paperSize.height`（μm）作为逃生门。
- **彩色问题定位**：配置窗口勾选「保留生成的 PDF」后，任务记录给出 PDF 绝对路径：
  PDF 黑白 → 渲染/打印链路问题；PDF 彩色但出纸黑白 → 打印机或驱动（默认单色、
  队列侧需开启 `print-color-mode`）。
- **macOS 分发包**：绿色版未签名，首次需右键 → 打开。
