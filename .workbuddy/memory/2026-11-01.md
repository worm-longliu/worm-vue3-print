## 审查 GitHub PR #11「表格明细按值纵向合并（mergeSameValue）」

用 `git fetch github pull/11/head` + 临时 worktree（/tmp）在 PR 分支与 master 上跑对照复现，已清理工作树与临时分支。

实测结论（两个真实缺陷，PR 自带 529 条 render 测试全绿，说明测试没覆盖）：

1. **分页致命**：归并在切片前完成，合并段变成 `buildRowGroups` 的 keep-together 组 → 段高超过一页即整表无法分页。
   实测 40 行 × 10mm（页可用 275mm）：不合并 = 2 页（270+150mm）；开合并（单位列全"个"）= 首页只剩表头 10mm + 次页 41 行 410mm 越界，`overflow` 仍为 false，`.print-page{overflow:hidden}` 静默裁切；带小计行时首页渲染"小计 0"。
2. **存量修复回归**：`data-binder.ts:161-163` 无条件 `cell.merged = false`，把数据行**横向**合并（colspan 主格 + merged 占位）的占位格清成真 td → 行多出一列（spanSum 3 vs 2）。master 上同一用例正确。

建议口径：归并挪到切片之后（行数/行高不变，无循环依赖），跨页按 Word 口径拆段并在续页重放值；若坚持 keep-together 必须加"段高 > 页高则降级拆分 + 补 td + 置 overflow"。

## 修复实现：分支 `feat/merge-same-value-pagination`（基于 PR #11 头提交 72626ba）

核心改动：归并从绑定阶段移到**渲染区间**。

- `row-merge.ts`：`mergeDataRowsByValue`（原地改写 `_renderRows`）→ `buildMergeOverlay(rows, start, end)`，返回 `{ rowspan: Map<'r:c',n>, merged: Set<'r:c'> }`，只描述本区间，不改共享渲染行。段边界规则：仅 data 行、两侧都声明 `mergeSameValue`、文本全等且 `trim()` 非空、横排占位格（`merged`）作边界、`rawFormatter` 列整列跳过。
- `html-generator.ts: renderMatrixRows`：算 overlay，占位格跳过、`mergedSpan` 优先于静态 rowspan，并用 `{...cell, rowspan: span}` 作为有效格喂 `cellFitCapMm`（合并格可用高度）。header 重复走 `rowLimit`，与 overlay 不冲突（表头无 data 行）。
- `data-binder.ts`：删掉归并调用；`mergeSameValue` 进 `makeRenderRow` 白名单（只在为 true 时带字段）；新增 `resetDataRowSpan()` 只清"被上方行覆盖"的 `merged`，横向合并占位格保留（原实现无条件清 `merged` 会把 data 行 colspan 占位格变成空 td，整表错列）。
- 分页引擎零改动：mergeSameValue 不再产生 rowspan，`buildRowGroups` 看不到跨行主格，长明细照常切片。

实测（A4/页可用 275mm/行高 10mm）：40 行 → 2 页 [0,27)/[27,41)，rowspan 26/14，明细 40 行全在纸内；100 行 → 4 页，rowspan 26/26/26/22。带小计行 → 首页 25 条小计 25、次页 15 条小计 15。

测试：core 81 文件/1174 通过（个别 worker 启动超时，单跑通过）；canvas 77/744 通过；common 360/364，4 条失败均为 `vi.spyOn(window,'alert')` 的 jsdom 环境问题，pr11-base 上同样失败（已用对照 worktree 确认）。
